# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

MasilMuscle is a Korean-language, mobile-first (dark UI) workout management web app for regular members and trainers, backed by Supabase (Auth + Postgres). The whole frontend is a single static file, `index.html` (inline `<style>` + one inline `<script>`; `@supabase/supabase-js` is loaded from the jsdelivr CDN). There is no build system, package manager, linter, or test suite.

Other files: `supabase/schema.sql` (tables, auth trigger, RLS policies — run once in the Supabase SQL editor), `supabase/auth_trigger.sql` (the signup-profile trigger alone, idempotent), `supabase/migration_002_mypage_inbody.sql` (idempotent, run after the others: profile info columns + `trainer_code`, `workout_logs.note`, `inbody_records`, PT `requested` status, self-profile update guarded by the `guard_profile_update` trigger, and the `my_trainer_code` / `link_trainer` / `unlink_trainer` RPCs), `supabase/migration_003_inbody_fields.sql` (`inbody_records.fat_mass`, `visceral_fat`; InBody input mirrors the user's sheet: weight, muscle, fat mass, visceral level — `fat_pct` is computed on save, BMI from profile height), `supabase/exercises.sql` (idempotent: `exercises` table + RLS + seed of ~376 exercises, and drops the `workout_logs.part` check) and `.github/workflows/keep-supabase-alive.yml` (daily 09:00 KST GET to the REST API; needs `SUPABASE_URL` and `SUPABASE_ANON_KEY` repo secrets).

## Brand (믓 · MOVE & STRENGTH)

The app is branded **믓** (MasilMuscle is the repo/legacy name). `brand/README.md` is the design system: logo symbol (a bold geometric 믓 glyph — ㅁ·ㅡ·ㅅ only, no dot or extra marks; SVGs in `brand/`), colors (IRON BLACK #171717, CHALK WHITE #F2F0E9, FIELD GREEN #B5C49C = workout state, PULSE TEAL #4FB3A0 = accent/primary action (`--accent`; replaced rust orange); warnings use mustard `--warn` #D9A05B, CONCRETE #77736D, GRAPHITE #333333; ratio 55/30/10/5), type (Pretendard + IBM Plex Mono for short English labels/numbers only), sizes (20px gutter, 8px grid, 6px radius, 4px chips, 48–52px controls) and copy tone (e.g. 저장 → "오늘도 한 건 했다.", new best weight → "오, 이건 좀 믓지다."). In `index.html` use the role tokens (`--bg --card --card2 --line --t --m --p`) rather than raw hex; `.card.hl` is the chalk-white highlight card that re-scopes those tokens for dark-on-light. UI uses inline 2px line icons (`ICON`/`ico()`), not emoji. Secondary text must be `--m` (#9A958D), since CONCRETE fails contrast for small text.

## Running

No build step. Serve statically (e.g. `python3 -m http.server`) and view at mobile width (`max-width:480px`). `SUPABASE_URL` at the top of the script is the project base URL (`https://<project-ref>.supabase.co`, no `/rest/v1/` suffix; the auth screen warns if it is the bare `supabase.co`). The anon/publishable key is public by design; security comes from RLS. There are no tests; to check UI changes, load the page with Playwright and stub the CDN script or point it at a real project.

## Architecture

Vanilla JS, no framework or modules; order in the `<script>`: config → domain constants → state/utils → auth → data loading → recommendation → views → `render()`.

- **State**: one in-memory object `st` (`me` profile, `tab`, `mode`, `members`, `sel` selected member, `logs`, `pts`, `draft` record form, ...). Nothing is persisted locally; the Supabase session is persisted by supabase-js. Pattern: call a Supabase mutation through `ok(await sb...)` inside `run(...)` (toasts errors), then `loadData()` and `render()`.
- **Rendering**: `render()` rebuilds `#app` innerHTML from template strings. Handlers are inline `onclick`/`onchange`, so they must stay global. Always wrap user text in `esc()`. Form inputs update `st.draft` via `oninput` without re-rendering (to keep focus); steppers/chips re-render.
- **Roles & modes**: `profiles.role` is `member` or `trainer`. A trainer has two modes (`st.mode`): `trainer` (`coaching()` true: members/record/history/pt tabs, acting on the selected member `st.sel`) and `personal` (same screens as a member, on their own data). `targetId()`/`targetProfile()` resolve whose data the current screen reads/writes; records created while coaching get `is_pt: true`.
- **Exercise catalog**: body parts (`PARTS`, 11 values from the CSV: 전신, 하체, 등, 가슴, 어깨, 이두, 삼두, 복근_신전근, 필라테스, 애니멀플로우, BASIC) and their exercises come from the Supabase `exercises(body_part, name)` table, loaded into `st.exercises` by `loadExercises()` at login; `exercisesOf(part)` merges it with exercises already in the user's logs. Saving a log with a name not in the catalog upserts it into `exercises` (ignore duplicates). `workout_logs.part` stores the body_part value; legacy `팔` logs still count toward 이두/삼두 rest days.
- **Data model** (see `supabase/schema.sql`): `profiles` (role, level 초급/중급/고급, `trainer_id`, `notes`, `curriculum`), `workout_logs` (`user_id`, `log_date`, `part`, `exercise`, `sets` jsonb `[{w,r}]`, `feedback`, `is_pt`), `pt_schedules` (`member_id`, `trainer_id`, `pt_date`, `pt_time`, `goal`, `status` scheduled/completed/canceled). A DB trigger creates the `profiles` row from signup metadata (`name`, `role`, `level`); the client only inserts a fallback profile if it is missing. Changing columns/policies means updating both `schema.sql` and the client queries.
- **RLS drives the trainer features**: trainers can read member profiles (to look up by exact email) and claim only unassigned members (`trainer_id` null → self); trainers can read/insert/delete logs and manage PT rows only for their own members; members can read their trainer's profile. Policies use `security definer` helpers (`is_trainer`, `my_trainer_id`, `is_my_member`) to avoid recursion.
- **Tabs**: member/personal mode = 홈(weekly calendar strip with 운동/PT/인바디 dots; tapping a day filters history by `st.hf.date`) · 기록 · 히스토리 · 인바디 · 수업 (members only: PT request/cancel, upcoming PT, PT logs with trainer feedback/note) · 마이 (내 정보, trainer-code linking, font size via `body.style.zoom` in localStorage). Coaching mode = 회원 (incl. pending PT requests to approve) · 기록 · 히스토리 · 인바디 · PT · 마이 (shows the trainer's 4-digit code).
- **Trainer linking**: a member links by entering the trainer's 4-digit code (`link_trainer` RPC); trainers can also claim members by email. Members cannot change `role`/`trainer_id`/`notes`/`curriculum`/`trainer_code` on their own row (trigger reverts them; RPCs bypass via `app.bypass_guard`). If the migration has not been run, `st.needMig` shows a hint and the app degrades (no inbody, note only sent when non-empty).
- **Recommendation engine** (`recommend`, `suggest`, `topExercises`): split per level in `PLANS` (초급 상체/하체, or 전신 when no logs; 중급 밀기/당기기/하체; 고급 4분할). Picks the group whose most recently trained part rested longest. Progressive overload per exercise from the latest log: all sets ≥ `TARGET_REPS[level]` (12/10/8) → weight +2.5kg (≥40kg) or +1kg (bodyweight → +1 rep); otherwise same weight, +1 rep. A latest log per part whose feedback matches `통증|부상` triggers a warning card.
- **Large reads**: Supabase returns at most 1000 rows per request, so lists that can exceed that (`workout_logs`, `exercises`) are loaded with `fetchAll(() => query)`, which pages with `.range()`. Keep a stable `.order()` (with `id` as tiebreaker) on such queries.
- **History search**: the history tab filters the already-loaded `st.logs` client-side via `st.hf` (text query over exercise/feedback, body-part chips, exercise dropdown); picking an exercise shows a summary (count, best set, last date), a per-set-number min/max weight table (like the sheet's "운동별 최대/최소 무게") and a compact date | kg×reps table of every past session. Feedback is collapsed by default (💬 toggle); the date sort toggle (`st.hf.sort`) reverses the newest-first `st.logs`. Delete buttons only appear while "삭제 모드" (`st.hf.edit`) is on, to prevent mis-taps. The record tab shows the last 3 records of the chosen exercise.
- **Dates**: use `today()` / `localDate()` (timezone-corrected `YYYY-MM-DD`), not `toISOString()` directly.
